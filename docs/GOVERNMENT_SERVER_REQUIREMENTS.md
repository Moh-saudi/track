# متطلبات تجهيز السيرفر الحكومي لمنظومة المسؤولية الطبية

> هذا المستند هو مرجع تجهيز بيئة الإنتاج. لا يحتوي كلمات مرور أو مفاتيح فعلية.  
> المعمارية المستهدفة تفترض أن **جميع مستندات القضايا والمرفقات ستُحفظ مستقبلًا على تخزين حكومي دائم** وليس على Vercel أو قرص مؤقت.

## 1. المعمارية المطلوبة

يفضل فصل المكونات إلى ثلاث طبقات داخل الشبكة الحكومية:

1. **Reverse Proxy / WAF** يستقبل HTTPS فقط.
2. **Application Server** لتشغيل Next.js/Node.js، ولا يكون مكشوفًا مباشرة للإنترنت.
3. **PostgreSQL Database Server** على شبكة داخلية خاصة.
4. **Persistent Document Storage** قرص/Volume/NAS داخلي دائم لمرفقات القضايا وبطاقات الرقم القومي.
5. **Malware Scanner** باستخدام ClamAV/clamd لفحص كل ملف قبل اعتماده.
6. **Backup Target منفصل** عن التخزين الرئيسي.
7. يفضل ربط السجلات التشغيلية والأمنية بـ **SIEM / Central Log Server** الحكومي إن كان متاحًا.

لا يتم تقديم مجلد المرفقات كـ static files من Nginx. كل تنزيل يجب أن يمر عبر التطبيق بعد التحقق من الجلسة والصلاحيات.

## 2. مواصفات الخوادم المقترحة

### Application Server

الحد الأدنى المقبول لبداية إنتاج متوسطة:

- Linux LTS معتمد لدى الجهة: Ubuntu Server 24.04 LTS أو RHEL/Rocky/AlmaLinux مكافئ.
- 4 vCPU حد أدنى.
- 16 GB RAM.
- 80–100 GB SSD للنظام والتطبيق والـlogs المؤقتة.
- Node.js 22 LTS.
- Nginx حديث ومدعوم.
- خدمة التطبيق تعمل بحساب Service Account مخصص **بدون root**.
- لا يتم تثبيت أدوات التطوير غير اللازمة على خادم الإنتاج.

الموصى به إذا كان عدد المستخدمين أو المرفقات كبيرًا:

- 8 vCPU.
- 16–32 GB RAM.
- فصل Application عن Database وعن Document Storage.

### PostgreSQL Server

- PostgreSQL 16 أو إصدار أحدث معتمد لدى الجهة.
- 4 vCPU حد أدنى، و8 vCPU موصى بها.
- 16 GB RAM حد أدنى، و32 GB موصى بها عند زيادة السجلات والتقارير.
- SSD سريع، ويفضل RAID مناسب للتوافر.
- مساحة أولية لقاعدة البيانات: 200–500 GB قابلة للتوسع حسب حجم السجلات والـAudit.
- المنفذ 5432 متاح فقط من خادم التطبيق/شبكة الإدارة، وليس من الإنترنت.
- تشفير القرص At Rest من طبقة التخزين الحكومية.
- نسخ احتياطي PostgreSQL + WAL/PITR إذا كانت البنية تسمح.

> مستندات القضايا لا تُخزن داخل PostgreSQL؛ قاعدة البيانات تحفظ metadata ومسار الملف فقط.

## 3. تخزين مستندات القضايا — نقطة حرجة

المسار المقترح:

`/srv/medical-liability/uploads`

ويتم تمريره إلى التطبيق:

`UPLOAD_ROOT=/srv/medical-liability/uploads`

البنية الداخلية ينشئها التطبيق، ومنها:

- `case-attachments/<case-id>/`
- `doctor-national-id/`
- `.quarantine/`

الصلاحيات:

- مالك الملفات: Service Account الخاص بالتطبيق.
- المجلدات: 0750.
- الملفات: 0640.
- لا يوجد وصول مباشر عبر URL إلى هذا المجلد.
- لا يستخدم المستخدمون SSH للوصول للمستندات.

### حساب السعة

لا يمكن تثبيت رقم نهائي بدون متوسط القضايا والمرفقات الحقيقي. تستخدم المعادلة:

`القضايا سنويًا × متوسط الملفات لكل قضية × متوسط حجم الملف × سنوات الاحتفاظ × 1.30`

الـ30% الأخيرة Headroom للنمو والفهارس والنسخ المؤقتة.

أمثلة تخطيطية فقط، إذا كان المتوسط 10 مستندات لكل قضية وحجم المستند 5MB:

| القضايا/سنة | بيانات جديدة/سنة | 5 سنوات + 30% Headroom |
|---:|---:|---:|
| 5,000 | ~250 GB | ~1.63 TB |
| 10,000 | ~500 GB | ~3.25 TB |
| 20,000 | ~1 TB | ~6.5 TB |

إذا كان الحمل المتوقع قريبًا من 10,000 قضية سنويًا، **4 TB usable قابلة للتوسع** بداية معقولة للتخزين الأساسي، لكن يعتمد الرقم النهائي على إحصاءات الجهة.

التخزين يجب أن يكون قابلًا للتوسع بدون تغيير مسار التطبيق: LVM / SAN / NAS / Enterprise Volume.

**RAID ليس Backup.** النسخة الاحتياطية يجب أن تكون على Target آخر.

## 4. حدود رفع الملفات

القيمة الافتراضية الحالية:

`MAX_UPLOAD_MB=25`

الملفات المسموحة للقضايا:

- PDF
- PNG
- JPEG
- DOC
- DOCX

بطاقة الرقم القومي: PDF فقط وبحد 12MB.

التطبيق يتحقق من:

- الحجم.
- الامتداد.
- التوقيع الفعلي Magic Bytes.
- اسم تخزين عشوائي وغير قابل للتنبؤ.
- عدم Path Traversal.
- حجر الملف مؤقتًا.
- فحص Malware قبل نقله للمسار النهائي.

على الإنتاج:

`MALWARE_SCAN_MODE=required`

ويجب تجهيز:

- `clamd`
- `clamdscan`
- تحديث signatures تلقائيًا عبر freshclam أو Mirror داخلي معتمد.
- مراقبة فشل أو توقف خدمة الفحص.

عند توقف Antivirus في وضع `required` يتم **رفض الرفع** بدل قبول ملف غير مفحوص.

## 5. الشبكة والجدار الناري

### من الإنترنت / شبكة المستخدمين

السماح فقط:

- TCP 443 إلى Reverse Proxy.
- TCP 80 اختياري فقط لإعادة التوجيه إلى HTTPS، ويمكن إغلاقه إذا لم يلزم.

### Application Server

- Port 3000: localhost أو الشبكة الداخلية فقط.
- SSH 22: من Jump Host/VPN وعناوين إدارة محددة فقط.
- لا يفتح 3000 للعامة.

### Database

- 5432 من Application Server فقط.
- لا يوجد Public IP لقاعدة البيانات.

### Storage / NAS

- يسمح فقط لخادم/خوادم التطبيق ونسخ الاحتياطي.
- البروتوكول حسب سياسة الجهة (NFSv4/SMB Enterprise/SAN)، مع تشفير الشبكة حيث يلزم.

## 6. HTTPS وTLS

مطلوب:

- شهادة TLS صادرة من الجهة الحكومية/CA المعتمدة.
- TLS 1.2 وTLS 1.3 فقط.
- منع البروتوكولات والـciphers القديمة.
- HSTS بعد التأكد من عمل النطاق بالكامل على HTTPS.
- DNS رسمي ثابت.
- NTP موحد مع مصادر الوقت الحكومية.

التطبيق يضيف Security Headers أيضًا، ومنها CSP وnosniff وDENY framing وReferrer Policy.

يجب تنفيذ فحص TLS خارجي/داخلي قبل Go-Live طبقًا لأداة الجهة.

---

## 7. Secrets ومفاتيح التشفير

المتغيرات السرية لا تُحفظ في GitHub ولا داخل ملفات المشروع.

مطلوب على الإنتاج:

- `DATABASE_URL`
- `NEXTAUTH_SECRET`
- `FIELD_ENCRYPTION_KEY`

توليد أمثلة:

`openssl rand -base64 48`

`openssl rand -hex 32`

يجب أن يكون `FIELD_ENCRYPTION_KEY` محفوظًا في Secret Vault أو ملف Environment محمي `0600` وتوجد منه نسخة Escrow مشفرة ومصرح بها؛ ضياعه يعني فقد القدرة على قراءة البيانات المشفرة.

لا تستخدم نفس المفتاح في Development وStaging وProduction.

بعد ترحيل البيانات القديمة وتشغيل الاختبار:

`REQUIRE_ENCRYPTED_SENSITIVE_FIELDS=true`

## 8. إعدادات المصادقة

الإعدادات المقترحة:

`SESSION_MAX_AGE_SECONDS=28800`

`LOGIN_MAX_FAILURES=5`

`LOGIN_RATE_WINDOW_MINUTES=15`

`LOGIN_BLOCK_MINUTES=15`

التطبيق الآن:

- يستخدم bcrypt.
- يمنع كلمات المرور الضعيفة.
- الحد الأدنى 12 حرفًا مع حروف كبيرة وصغيرة ورقم ورمز.
- يطبق Rate Limit لمحاولات الدخول.
- يلغي الجلسات القديمة عند تغيير كلمة المرور أو الدور أو تعطيل المستخدم.
- يعيد التحقق من حالة المستخدم أثناء الجلسة.

### MFA / SSO

للاعتماد الحكومي النهائي يوصى بشدة بربط المنظومة بـ IdP حكومي/Active Directory/Keycloak أو مزود OIDC/SAML مع MFA إذا كان متاحًا لدى الجهة.

هذا الجزء يحتاج بيانات الـIdP الفعلية من مهندس الهوية، لذلك لا يمكن اختباره داخل المشروع قبل توفير:
- Issuer/Metadata.
- Client ID.
- Redirect URIs.
- Group/Role mapping.
- MFA policy.

حتى توفير ذلك، Credentials الحالية تعتبر وضعًا انتقاليًا يخضع لموافقة سياسة أمن الجهة.

## 9. إعدادات المالية

قيم البدلات لا تكون Hard-coded في Production.

يقدم المسؤول المالي/الإداري القيم المعتمدة، وتوضع كـ:

`SUBCOMMITTEE_SESSION_ALLOWANCE=<القيمة المعتمدة>`

`SUPREME_SESSION_ALLOWANCE=<القيمة المعتمدة>`

إذا لم يتم تعريف القيم في Production، يفشل إنشاء الاستحقاقات بدل استخدام رقم افتراضي.

المبالغ مخزنة في PostgreSQL كـ `DECIMAL(12,2)` وليس Floating Point.

## 10. أول تشغيل

### قاعدة موجودة حاليًا

قبل أي Migration:

1. Backup كامل لقاعدة البيانات.
2. Backup/Copy لمجلد uploads الحالي إن وجد.
3. تشغيل:
   `npm run preflight:production`
4. معالجة أي تكرارات/مشاكل تظهر.
5. تشغيل ترحيل البيانات الحساسة:
   `npm run data:migrate-sensitive`
6. عند نقل ملفات قديمة من مسار مختلف، ضبط `LEGACY_UPLOAD_ROOT` وتشغيل:
   `npm run data:migrate-attachment-paths`
7. نسخ الملفات إلى `UPLOAD_ROOT` مع الحفاظ على المسارات النسبية.
8. تطبيق Migration:
   `npm run db:deploy`
9. تشغيل Preflight مرة أخرى.
10. ضبط:
    `REQUIRE_ENCRYPTED_SENSITIVE_FIELDS=true`
11. تشغيل Preflight للمرة النهائية.
12. Build ثم Start.

### قاعدة حكومية جديدة

المشروع الحالي بدأ تاريخيًا قبل إنشاء Migration Baseline كامل. لذلك **لا يتم تشغيل migration الأمني على قاعدة فارغة**.

المسار المعتمد هو:

1. أخذ `pg_dump` من قاعدة البيانات المقبولة.
2. `pg_restore` إلى PostgreSQL الحكومي.
3. Preflight.
4. Migration الأمني.
5. Post-migration validation.

أي إنشاء قاعدة فارغة من الصفر يجب أن يتم في نافذة تجهيز منفصلة مع Baseline معتمد.

## 11. إنشاء أول مدير

الـseed لا ينشئ أي حسابات ولا يحتوي كلمات مرور افتراضية.

أثناء نافذة التجهيز فقط:

- ضع `INITIAL_ADMIN_EMAIL`
- ضع `INITIAL_ADMIN_PASSWORD` قوية
- شغّل `npm run admin:bootstrap`
- احذف `INITIAL_ADMIN_PASSWORD` فورًا من Environment/Secret staging area.
- سجل العملية في محضر التجهيز.

البرنامج يمنع الـbootstrap إذا كان هناك ADMIN نشط بالفعل.

## 12. Backup وDisaster Recovery

يجب نسخ **قاعدة البيانات + ملفات المستندات** معًا.

الحد الأدنى المقترح:

- PostgreSQL Backup يومي.
- WAL/PITR إن كان متاحًا.
- Incremental للملفات يوميًا.
- Full Backup أسبوعي.
- نسخة خارج خادم الإنتاج/Storage الرئيسي.
- تشفير النسخ الاحتياطية.
- Retention يحدد رسميًا حسب سياسة الجهة.
- اختبار Restore دوري وليس مجرد التحقق أن Job نجح.

اقتراح أهداف للمناقشة مع الجهة:

- RPO: 24 ساعة كحد أقصى، ويفضل أقل.
- RTO: 4 ساعات أو حسب تصنيف الخدمة.

إذا كانت الخدمة حرجة وتحتاج RPO أقل، يلزم replication/WAL archiving ونسخ ملفات أكثر تكرارًا.

اختبار الاستعادة يجب أن يثبت أن metadata الخاصة بالمرفقات تتطابق مع الملفات الفعلية.

## 13. Logs وMonitoring

مطلوب مراقبة:

- Nginx access/error logs.
- Application logs.
- PostgreSQL logs.
- ClamAV logs.
- Disk usage وInodes.
- CPU/RAM/load.
- فشل النسخ الاحتياطي.
- فشل Antivirus signatures.
- TLS certificate expiry.
- 4xx/5xx spikes.
- Audit events داخل التطبيق.

يفضل إرسال السجلات إلى SIEM داخلي مع Retention غير قابل للمسح من مستخدم التطبيق.

يجب ألا تحتوي logs على:
- كلمات مرور.
- أرقام حسابات كاملة.
- IBAN كامل.
- أرقام كروت.
- الرقم القومي.
- محتوى ملفات المرضى.

## 14. CI/CD ومتطلبات الكود

المشروع يحتوي Pipeline أمني يقوم بـ:

- `npm ci` من lockfile.
- Prisma generate.
- PostgreSQL حقيقي داخل CI.
- تطبيق قيود DB الأمنية.
- TypeScript typecheck.
- اختبارات Security Regression.
- Seed reference-only.
- اختبارات قيود قاعدة البيانات وLogin Throttling.
- Production Preflight.
- `npm audit --audit-level=high`.
- Production build.
- إنشاء CycloneDX SBOM.
- CodeQL.

قبل الدمج إلى `main` يجب أن تكون الاختبارات ناجحة.

يوصى بحماية `main` من GitHub Settings:
- Require Pull Request.
- Require successful Security CI.
- Require CodeQL.
- منع Force Push/Delete.
- تفعيل Secret Scanning وDependabot alerts إن كانت متاحة.

## 15. فحوص القبول قبل Go-Live

يوقع عليها مهندس التطبيق + الأمن + البنية التحتية:

- [ ] لا توجد حسابات Demo أو كلمة مرور افتراضية.
- [ ] TLS 1.2/1.3 فقط.
- [ ] قاعدة البيانات غير مكشوفة للعامة.
- [ ] Application port غير مكشوف للعامة.
- [ ] Firewall rules موثقة.
- [ ] ClamAV يعمل وملف EICAR الاختباري يتم رفضه وفق إجراءات الأمن.
- [ ] ملفات غير صحيحة الامتداد/التوقيع يتم رفضها.
- [ ] ملف أكبر من الحد يتم رفضه.
- [ ] لا يمكن تنزيل مرفق قضية بدون صلاحية.
- [ ] مستخدم لجنة لا يرى قضية لجنة أخرى.
- [ ] مستخدم غير مالي لا يرى مبالغ/حالات صرف.
- [ ] تعطيل المستخدم يبطل جلساته.
- [ ] تغيير الدور يبطل الجلسة القديمة.
- [ ] خمس محاولات دخول فاشلة تؤدي للحظر المؤقت وفق الإعداد.
- [ ] لا توجد قيم حساسة plaintext بعد migration.
- [ ] لا يمكن تكرار caseNumber + caseYear.
- [ ] لا يمكن إنشاء استحقاق مالي مكرر.
- [ ] لا يقبل مبلغًا سالبًا.
- [ ] Audit log لا يحتوي أسرارًا.
- [ ] Backup ناجح.
- [ ] Restore فعلي ناجح في بيئة اختبار.
- [ ] اختبار امتلاء Storage/تنبيه 80% و90%.
- [ ] Vulnerability Scan للبنية.
- [ ] Penetration Test للتطبيق.
- [ ] فحص Headers/CSP.
- [ ] Load Test حسب عدد المستخدمين المتوقع.
- [ ] خطة Incident Response وأرقام التواصل معتمدة.

## 16. معلومات نحتاجها من مهندس الجهة لتثبيت المقاسات النهائية

قبل شراء/حجز Storage نهائيًا نحتاج:

- عدد القضايا المتوقع سنويًا.
- متوسط عدد الملفات لكل قضية.
- متوسط/أقصى حجم للمستند.
- مدة الاحتفاظ القانونية.
- عدد المستخدمين المتزامنين المتوقع.
- هل يوجد NAS/SAN قائم؟
- هل يوجد Load Balancer/WAF؟
- هل يوجد Active Directory/SSO/IdP؟
- هل يوجد SIEM؟
- سياسة Backup وOff-site.
- RPO/RTO المطلوبان.
- هل البيئة متصلة بالإنترنت لتحديث AV/dependencies أم تستخدم Mirrors داخلية؟

بناءً على هذه الأرقام يتم اعتماد CPU/RAM/Storage النهائي بدل الاعتماد على تقدير عام.
